# 麻雀ドメイン共通核の導入計画案

**作成日:** 2026-11-16

**状態:** 提案。共通核の実装、依存更新、ライセンス変更は未着手。

**対象:** [shanten](../README.md)、
[mahjong-formalization][formalization]、
利用元の[aka37][aka37]。
比較基準はshanten `27d41d7`、分類側 `bd84dd915b8fade0a8d04746a60021e4028848e7`、
aka37 `a945c9e36c2ae0c407e20e0f45da4f041d75b8c8`。

## 1. 目的と提案

麻雀の**ドメイン知識・語彙・不変条件を一貫して獲得し、長期に安定させる**。
コードの行数削減や分類器・シャンテン計算器の統合は主目的ではない。

背景には、架空の天鳳IDを作らずにInt37で分類器へ入力する
[mahjong-formalizationのIssue #2][formal-issue-2]がある。
同IssueはGo分類APIの拡張として完了している。本計画はその考えを発展させ、
Int37・Int34とその対応をLeanで共通定義し、各プロジェクトが同じ意味に従うことを目指す。

そのために、Int37を含む牌の表現、変換、枚数制約、面子と通常形の基礎仕様を、
小さな独立したLeanライブラリに置くことを提案する。
両プロジェクトがこの核を利用し、実行可能な定義・証明・用語を同じ出典に結び付ける。
共通核の仮称を以下では「ドメイン核」と呼ぶ。リポジトリ名・公開API名は確定していない。

**方向性**

1. aka37のInt37の意味を共通仕様として明確化し、3プロジェクト間の不一致は課題として検出する。
2. 4枚制約を「対象となる牌の範囲」と一緒に定義し、既存の分類結果の合法性を維持する。
3. Leanとmathlibの版を合わせ、段階的に小さなドメイン核へ移す。
4. 定義の名前だけでなく、定義の前提・保存する情報・機械検証された定理まで語彙として管理する。
5. 各用途の固有仕様・API・出力と既存の証明保証は維持する。

この計画は[前回の調査](./MAHJONG_FORMALIZATION_REUSE_REVIEW_2026-11-16.md)の
「テストを先行し、共通核の抽出を後で判断する」という優先順位を変更する。
相互検証は抽出の必要な工程として残すが、独立核の実現を計画の目標に据える。

## 2. 前回報告の訂正と未解決課題

### Int37の意味は異ならない

前回の「入力コンテナは異なる」という記述は、Int37自体の意味が異なるように
読める表現だった。**そのような意味の差は確認していない。**

- aka37の[牌定数・容量・Int34への射影][aka-tile]、
  shantenの[Counts37と入力契約](../README.md#input)、
  分類側の[Int37入力契約][formal-go]は、0〜36の対応と
  赤5は1枚・通常5は3枚という容量について一致する。
- `Int37`は1枚の**赤を区別した牌種値**である。
  分類側の`[]int`はその値を枚数分並べた列、
  shantenの`Counts37`は同じ値ごとの枚数を保持する配列であり、
  **同じ牌種語彙の異なる集約表現**である。
- 両APIは対象手牌の枚数、固定面子、エラー分類が異なる。
  それをInt37の意味や、共通範囲での計算結果の差と混同しない。

ただし、個々の実装が一致していることを3リポジトリ間のLean定理として
今回証明したわけではない。後述の全値比較・保存定理を受入条件にする。
既存の[aka37 Int37契約][aka-contract]も成果物に反映する。

### 分類側も4枚制約を守る

前回の説明は、分類側の計算結果そのものが4枚制約を破るかのように
誤読され得た。**そのような不具合は確認していない。**
[IsWaitFor][formal-wait]は対象牌姿の各牌種4枚以下と待ち牌の5枚目排除を要求し、
直接生成側の[Seed.valid][formal-direct]も完成牌姿の4枚制限を検査する。
これらの対象範囲で、制約はソース上の述語にも表現されている。

一方、分類側の既存Finderが受け取るのは解析対象の牌姿だけであり、
別に固定された面子の実牌内容は受け取らない。
この**文脈の欠落**と4枚制約の不在は別問題である。
固定面子を持つ実手牌との対応において、共通の語彙・型・定理が
必要十分な文脈を明示していない点を、共通化で解消すべき課題とする。
分類側の既存結果が誤っているという結論や、既存分類の意味変更は導かない。

### 記録する課題

| ID | 課題 | 解消条件の要点 |
|---|---|---|
| D1 | Int37の意味と列／カウント表現の違いが文書上まぎらわしい | 37値・34値・各容器の対応を明示し、全値と容量を3者で照合 |
| D2 | 分類の4枚制約と固定面子込みの制約の対象範囲が区別しにくい | 対象牌集合と加牌時条件を型・定理・用語で明示 |
| D3 | 物理IDからの射影で失う情報と逆方向の補完が混同され得る | 各写像の保存・非単射性と補完の保証範囲を明示 |
| D4 | 同じドメイン語が別型・別証明になり、将来乖離し得る | 共通核を両Leanプロジェクトが実利用し、対応定理を維持 |
| D5 | Lean／mathlib版とライセンス方針が揃っていない | 版を固定・両方を再検証し、権利確認後にライセンスを整備 |

いずれも**課題**であり、現時点での実装バグ確定や解消済みを意味しない。

## 3. 安定させる語彙と情報の向き

### 3.1 三つの表現

| 語 | 値と意味 | 保存する情報 | 失う情報 |
|---|---|---|---|
| 天鳳物理牌ID | `0..135`。34牌種それぞれに4枚のID | 牌種・物理コピー識別子。赤ID `16, 52, 88` | これ単体では所有者・面子・鳴き元等を表さない |
| Int37 | `0..36`。赤5を通常5から分けた牌種値 | 牌種と赤／通常の別 | 同じInt37値を持つ物理コピーの識別子 |
| Int34 | `0..33`。赤5を通常5と同じ牌種にした値 | 色・数／字牌の牌種 | 赤／通常の別と物理コピー識別子 |

値の写像は次の一方向で決定的である。対象は**有効な値**に限る。
範囲外の生の整数や不正なコレクションには、それぞれ明示的な検証が必要。

```text
Tenhou ID (136種) --天鳳の赤ID規約--> Int37 (37種) --赤5統合--> Int34 (34種)
                                 └───────────────> 牌種ごとの枚数
```

aka37の[THCode2Tile][aka-tenhou]と[Tile.Int34][aka-tile]はこの向きを使う。
赤5mのID `16 -> 0 -> 4`、通常5mのID `17 -> 5 -> 4`。
通常1mのID `0`と`1`はいずれも`1 -> 0`。
`Tenhou -> Int34`は`id / 4`であり、二段階写像と一致することを全136値で検証する。

この写像は逆関数ではない。`Int34`の5mは元が赤か通常かを決められず、
`Int37`の通常牌も元の物理IDを一般には決められない。
適切な代表IDや赤の割当てを選ぶ**補完**は可能だが、元の情報の復元とは呼ばない。
単に「通常5を選ぶ」代表は、34カウントの5が4枚のとき通常5の容量3を超える。
コレクションの補完は容量と未使用の物理IDを考慮し、失われた情報を創出したことを明記する。

具体的な代表値を返す必要が生じた場合に限り、前提と保証を別々に定める。
例：有効な37カウントから重複のない物理ID集合を選び、順変換して元の37カウントが
得られること。これは**選んだ代表の射影が元の37表現に一致する**保証であって、
元の物理ID集合が復元できる保証ではない。
現行[normalIndex](../Shanten/Input37/Basic.lean#L38)も34牌種ごとに通常側を
選ぶ代表であり、赤の割当ての復元ではない。

### 3.2 値・集合・列・カウントを分ける

- 天鳳ID列：順変換の`map`自体は列の順序を保つ。ただし牌姿の構造判定では順序を忘れられる。
  物理IDの重複は不正。
- Int37列：同じ値の反復は複数枚を意味し、物理IDの重複ではない。
  値を数えれば37カウントになり、列を並べ替えてもカウントは同じ。
- 37カウント：`count37[i]`はそのInt37値の枚数。
  各構成要素で非負を検査し、必要な範囲を合算後に容量を検査する。
  shantenの生入力は符号付き整数なので、正規化前に負数を拒否する。
- 34カウント：赤を統合した牌種別枚数。`5m`は赤5mと通常5mの和。
  同じ34カウントでも赤の割当てが違い得る。

列の正規化とカウント化は情報を追加で失う。個別の写像、列の順序、
多重集合、カウントの意味を分けて証明し、すべてを曖昧に「変換」と呼ばない。
三麻・赤枚数の変更など、別ルールへの一般化は現段階の対象外。

## 4. 共通核の境界案

### 4.1 核に置くもの

| 層 | 共有する知識 | 主要な保証 |
|---|---|---|
| 基本語彙 | スート、数・字牌、34牌種、赤を区別した37牌種、必要な有限列挙 | 値域・列挙の網羅性・各名称との対応 |
| 物理表現 | 有効な天鳳IDとその牌種・赤判定 | 136値の写像・4コピー・赤ID規約 |
| 射影・集約 | 136→37→34、列／多重集合／37・34カウントの対応 | 合成一致、総数・多重度・順序に関する保存則、非可逆性の反例 |
| 容量 | 37の赤1／通常5が3／他4、34の4枚、対象牌の合算 | 検証前後の関係、加牌の条件、負数の非相殺 |
| 部品 | 対子、順子、刻子、槓とその構成牌 | 牌の枚数、開始位置、牌種ごとの占有数 |
| 通常形 | 雀頭1個と所定数の順子／刻子による分解仕様 | 同じ牌多重度の外延性、順列を超える分解の区別 |

「槓」は4枚占有する固定面子として定義し、
通常和了分解の手元面子候補に槓を追加するという意味ではない。
固定面子集合と手元牌を合算する**共通の容量概念**は核に置くが、
shanten固有の入力全体・遷移・最短距離は利用側に残す。
最初から自由なゲームルールの汎用フレームワークにはしない。

### 4.2 利用側に残すもの

```text
             小さな独立Leanドメイン核
        牌 / 136→37→34 / 容量 / 部品 / 通常分解
                    ↑              ↑
            shanten Lean      分類Lean
          距離・3形・入力検証    待ち核・既約性・分類
                    ↑              ↑
        将来のGo計算器       既存Go/Python分類器
                    └──── aka37 Go ────┘
```

矢印は仕様・依存の方向を示す。GoがLeanコードを直接実行するという意味ではない。
Go移植は共通の契約・検査データへ照合する。shantenのGo契約は引き続き標準ライブラリのみとし、
Leanドメイン核や分類パッケージへのGo依存を強制しない。
分類結果の分解・待ち牌・重複度・既存IDは失わず、shantenの最小距離探索と統合しない。

ドメイン核の文書・定義・定理を共通語の正本とし、
両側の[用語集](./GLOSSARY.md)と[分類側語彙][formal-vocabulary]は
共通語を参照して用途固有の説明を維持する。
aka37の既存Int37契約は外部互換契約として保持し、
Lean核との照合結果を明示する。名称の変更時は対応表・移行期間・契約版を設け、
別の説明が密かに「正」になる状態を避ける。

## 5. 4枚制約の表現と対応

最初に次の三つを別の命題として名前と対象範囲を明示する。

1. **牌姿内有効性:** 解析する牌姿だけで各34牌種が4枚以下。
2. **牌姿の合法な待ち:** 牌姿内有効性、対象の枚数、加牌後の通常形分解、
   および待ち牌が牌姿内ですでに4枚でないこと。
   これは現行の分類Finderの契約に対応する。
3. **固定文脈込みの合法な待ち:** 手元牌と固定面子の合算が有効で、
   さらに加牌後も合算容量を満たし、手元牌が必要な通常形へ分解されること。
   固定槓は同種4枚を占有する。役・フリテン・河・山の残りを評価する条件ではない。

有効な固定文脈、手元牌の枚数と残余面子数の整合を前提に、
分類の待ち集合を固定牌の残余容量で絞ったものと、
固定文脈込みの待ち集合の一致を証明する。
この性質は既存Finderを非固定文脈として使う際の**接続定理**であり、
証明前に成立済みとは扱わない。

shantenの[既存A/B例](../Shanten/Capacity/Examples.lean#L11)では、
同じ手元東1でも東の固定刻子の有無で完成可能性と値が変わる。
分類Leanは1枚形を扱うが、分類Goの公開APIは1枚形を扱わない。
加えてGo公開APIを使う例として次も回帰候補にする。

| 文脈 | 手元4枚 | 固定面子3組 | 期待する東待ち |
|---|---|---|---|
| A | `111m`＋東 | 東東東・`123p`・`123s` | 残余形の待ちにはあるが、固定文脈込みでは不可 |
| B | 同上 | 南南南・`123p`・`123s` | 両方で可 |

これは検証すべき具体例であり、今回新たに実行・証明した結果ではない。
共通核ではこの違いを「分類に4枚制限がない」と表現せず、
何を数えた制約かを名前・前提・定理から読み取れるようにする。
既存の残余形分類と、固定牌込みの新たな評価は別の契約として扱い、
既存の分類コード・既約性・病的プロファイルを黙って変更しない。

## 6. 実施順序と受入条件

### P0：仕様の固定と課題のトリアージ

- D1〜D5について、上記3コミットを基準に用語表・対応表・前提を確定する。
- 37値、34値、136 ID、物理コピー、列、カウント、対象牌集合の区別を整理する。
- 分類側の既存保証を確認し、牌姿単独と固定文脈を含む場合を混同しない。
- 語彙の正本、公開名前空間、独立リポジトリの名称・保守方法を決める。

**受入:** 対応する既存定義と、同値をまだ証明していない箇所を区別した語彙表がある。
論点は「Int37が違う」「分類で5枚が許される」といった未確認の断定で記録しない。

### P1：Lean・mathlibの版合わせ

- 初期候補はshantenが使用するLean／mathlib `v4.35.0`。
  分類側の`v4.28.0`からの移行を試し、両者と共通核が同一バージョンを使う。
  移行が困難なら、証明とツール互換性を確認した別の**共通の版**を選ぶ。
- 各`lean-toolchain`、Lake依存とmanifestを明示的に固定し、
  クリーン環境でも再現可能な構成を記録する。
- 依存版変更と共通型の移行は別の変更として検証する。

**受入:** 版を揃えた状態で両Lean公開入口をビルドし、
shantenの`assert_no_sorry`を含む既存検査が成功する。
分類側の`MahjongTests`と関連計算ターゲットも対象を明示して実行し、
時間のかかる全列挙は既存生成物・代表回帰との比較と分けて結果を記録する。
実測前に版更新の容易さ・必要時間を断定しない。

### P2：独立核の初版と対応定理

- 適切なライセンス・版固定・小さな公開入口を持つ独立核を作る。
  まず既存定義から必要な依存のみを抽出し、上記4.1の語彙を導入する。
- 全37値の対応・容量、全34値、全136 IDについて有限検査し、
  構造化された一般定理を可能な範囲で証明する。
- 元の3プロジェクトの実装・契約を根拠とする独立データを使い、
  同じ実装を二重に呼ぶだけのテストを避ける。

**受入:** 少なくとも次を核の公開定理または明示的な有限検査として持つ。

1. `Tenhou -> Int37 -> Int34 = id / 4`（有効な全ID）、
   全37値の射影と容量、赤3 IDの対応。
2. 37／34カウントへの射影は枚数・加算を保存し、
   有効37カウントから有効34カウントを得る。
   不正な負数、赤2枚、通常5が4枚を正規化によって受理しない。
3. 写像の非単射性を具体例で示す。補完を実装する場合は、
   容量を満たす代表の射影一致のみを示し、元のID復元とは主張しない。
4. 面子・槓の占有、加牌後の有効性、通常形の分解と多重度を表現する。
   分類の分解情報を潰さない。
5. 主要定理の推移的な`sorryAx`不在を検査し、
   `native_decide`等の追加の信頼境界は別途記録する。

### P3：既存2プロジェクトへの接続

- 共通核を両方からコミットまたは版で固定して参照し、
  既存型へのアダプタ・互換入口と往復／保存の定理を用意する。
  一気に全面書き換えせず、基礎型・射影・容量・分解仕様の順に移行する。
- 分類側の既存Finderと直接生成が牌姿内4枚制約を守ることを共通の容量語彙に接続する。
  別途、固定文脈込み待ちの接続定理とA/B例を追加する。
- shantenの既存容量付き完成・遷移・3形の仕様、13・14枚相当の探索定理、
  37種検証の結果と証明依存を維持する。
- aka37・分類Go・shantenの意味照合は、それぞれの公開入力範囲に応じて行う。
  共通核をGoの既存実装が共有していると誤認しない。

**受入:** 両プロジェクトが実際に共通核をimportし、型だけでなく
変換・容量・通常分解の共通定義または対応定理を出口証明に利用している。
既存の分類コード・ID・病的プロファイル・待ち分解・エラー、
shantenの数値・固定容量・Go契約が変化しない。
136 ID網羅、赤置換、重複物理ID、37容量違反、負数、槓、A/B、
特殊形のみのテンパイ、順列・複数分解の回帰を含める。

### P4：運用と変更管理

- 共通核の語彙、定理、証明依存、対応する両利用側のAPIを一覧化する。
- CIで共通核・両利用側の固定版を検査し、更新時は対応表・変更履歴・テストを同時更新する。
- 数値順序・表現の意味・容量・構造的待ちの意味の変更は破壊的変更として扱い、
  影響を評価して版を上げる。最適化だけの変更も既存の出力互換を検査する。
- 共通核が証明の単一依存点になるため、独立な定義による対照例・
  実行可能な回帰データを残す。共通化したコード同士の一致だけを正しさの証拠にしない。

## 7. MITライセンスについての意見

**shantenと新しい共通核をMITに揃える方針に賛成する。**
分類側は既に[MIT][formal-license]で、共通部品の利用・配布を理解しやすくできる。
ただし、shantenには調査時点で追跡されたLICENSEがなく、
同一作者・同一アカウントであるだけで既存コード全体の権利関係は確定しない。

実施前に権利者と取り込んだ第三者コード・貢献の条件を確認し、
必要な著作権表示・MIT許諾文を保持する。
分類側からコードを移す場合も元の表示を維持する。
共通核・shantenでの著作権表示名と年は権利者が決める。
依存するmathlib等のライセンスも別途尊重し、
MIT化を依存物全体のライセンス変更と解釈しない。
これは実務上の提案であり、法的判断の代替ではない。
今回の依頼は計画提案のためLICENSEファイル自体は追加しない。

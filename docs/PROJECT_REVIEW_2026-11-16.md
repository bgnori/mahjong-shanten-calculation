## 総評

**現行の抽象モデルに対する証明基盤としては良好。ただし、Go契約に適合する計算器としては未完成。**

面子手の一般探索は、既存ブロックの存在を仮定せず、有効な13枚相当手牌に対する
仕様一致・全域性まで到達している。過去レビューで問題になった「分解から経路を作らず、
経路の存在を前提にする」段階も、現在のバッチ走査の出口定理では解消している。
国士無双の最大値13も、閉形式の算術だけでなく最短到達距離の仕様上で証明されている。

一方、交換遷移は4枚制限を保存しない。さらに、固定面子を個数へ抽象化したモデルは、
Go契約上の異なる答えを区別できない。後者は既知の後続課題であり、現在の証明が
誤っているという指摘ではないが、契約対応に進む際の必須条件である。

本レビューは定義・主要定理の前提と接続・実行例を重点確認し、全体ビルドと追加の
Lean検査で裏付けた。全証明本文の独立した数学的再証明、クリーン環境の再構築、
外部サービス側のCI設定の監査まで行ったものではない。実装コードは変更していない。

## R1：交換遷移が4枚制限を保存しない

**根拠:** [HandStep](../Shanten/Specification.lean#L45)、
[exchangeHand_step](../Shanten/Exchange.lean#L59)、
[validCounts_exchangeHand](../Shanten/Exchange.lean#L84)。

ドロー分岐には `ValidCounts after` があるが、交換分岐にはない。
`exchangeHand_step` も、捨てる牌が存在して引く牌と異なることだけで遷移を構成する。

次の反例をLeanで確認した。

```text
開始：東4、南4、西4、北1、固定面子なし
操作：北を捨て、東を引く
終了：東5、南4、西4
```

開始手は `IsThirteenTileHand` を満たす。それでも `HandStep before after` と
`¬ ValidCounts after` が同時に成立する。したがって、一般の `ReachesHand` /
`ReachesCompletion` を「有効な手牌だけを通る経路」として利用することはできない。

**影響の限定:** `Complete` の全形には現在すでに4枚制限があり、不正な完成形を
許すという旧レビューの問題とは異なる。今回の反例だけで、既存の最小シャンテン値が
誤ると結論することもできない。七対子の専用交換には別途有効性保存の証明があり、
有効目標へ不足牌を補う交換も、引く牌を目標枚数未満に限定している。
問題は共有遷移関係そのものの保証と説明の不足である。

**推奨:** 交換分岐にも終了手の有効性を要求し、共有交換補題では
`validCounts_exchangeHand` を利用する。意図的に緩い関係を維持する場合は、
有効状態だけの到達関係を別に定義し、対象入力で最小距離が一致することを示す。
この後者の選択は追加の証明負担を伴うため、まず前者を検討したい。

**受入条件:** 上記操作は有効遷移として構成できず、有効な開始手からの遷移・経路の
有効性保存を証明できること。既存の探索一致・到達上限の定理も再検証すること。

## R2：固定面子の個数だけでは契約の数値を保持できない

**根拠:** [Hand](../Shanten/Core.lean#L32)、
[Complete](../Shanten/Specification.lean#L19)、
[Input](../shanten.go#L28)、
[入力の合算容量制約](../README.md#input)。

現行Leanモデルが固定面子の容量検証を表現できない点は
[現行計画](./SHANTEN_LEAN4_PLAN.md#目的と維持する契約) に正しく明記されている。
ただし、入力検証をGo側で済ませれば残りの計算がそのまま正しくなる、という関係ではない。

次の二つは、どちらも入力時点では合算4枚制限に違反しない。

| 入力 | 手元牌 | 固定面子4組 | 容量制約を守る完成までの距離 |
|---|---|---|---|
| A | 東1 | 東東東、123萬、123筒、123索 | 2手：東を別種へ交換し、対子にする |
| B | 東1 | 南南南、123萬、123筒、123索 | 1手：東を引いて対子にする |

両者はLeanでは同じ「東1、`fixedMelds = 4`」になる。
この抽象手牌について、一般探索が `some 0` を返し、
`IsShapeShanten ... .mentsuHand 0` が成立することをLeanで確認した。
しかしAで東の対子を作ると、固定刻子と合わせて東5枚になる。
他の牌を1枚引いても雀頭にならないため、契約の容量制約を保つ距離は2、値は1である。
Bの値は0なので、抽象化後の同一入力から両者の正しい値を復元することはできない。

これは見えている牌・山の残り枚数の評価ではなく、入力自身が占有する牌の容量の問題である。

**推奨:** 固定面子の内容、またはそこから導出した牌種別の残余容量をモデルに持たせる。
入力だけでなく完成目標・ドロー・交換も、その容量に従うようにする。
槓は1面子・消費4枚であり、赤5統合前の37種容量検証との対応も別途必要になる。

**受入条件:** AとBを区別し、期待値1と0を検証すること。現行モデルから新モデルへの
対応条件と、既存定理を再利用できる範囲を明示すること。

## R3：自動検証と証明依存の継続的な検査がない

**根拠:** 対象コミットの追跡ファイル一覧に `.github/workflows/` は存在しない。
[READMEの検査手順](../README.md#checks) と
[台帳の検証記録](./SHANTEN_LEAN4_PROGRESS.md#検証記録) が現在の検証手段である。

Leanの回帰例は [Examples](../Shanten/MentsuHand/Examples.lean) に存在し、公開入口から
ビルドされる。Goに数値テストがないことも、計算器未実装という現在の範囲では妥当である。
不足しているのは、それらを変更のたびに実行するリポジトリ内の仕組みである。
外部CIやbranch protectionの有無は今回確認していない。

また、`lake build` の成功だけでは `sorry` の混入を拒否できない。
今回、主要10定理の依存に `sorryAx` はなかったが、その確認も手動である。

**推奨:** Go要件に合うツールチェーンで `go test ./...` / `go vet ./...`、
固定済みLean・Mathlibで `lake build` を自動実行する。主要出口定理について
`sorryAx` を拒否する検査を追加し、既存の `native_decide` 依存の扱いは区別して定める。
現存する全警告を即時エラー化するより、まずビルド失敗・証明穴を確実に検出する方がよい。

**受入条件:** 変更時に自動実行され、壊れたimport・証明・Go契約と証明穴を検出できること。

## R4：開発コンテナとGo要件が不一致

**根拠:** [go.mod](../go.mod#L3) は `go 1.26.4`。
一方、[dev用Dockerfile](../.devcontainer/dev/Dockerfile#L1) と
[user用設定](../.devcontainer/user/devcontainer.json#L3) はGo 1.24系イメージを使う。

今回の環境ではGo 1.24.5・`GOTOOLCHAIN=local` で、READMEどおりの両Goコマンドが
バージョン不足で失敗した。`GOTOOLCHAIN=auto` による1.26.4の取得後は成功した。
従って常に実行不能なのではないが、自動取得への依存が開発環境の説明に現れていない。

**推奨:** コンテナを要求するGo系統に合わせるか、自動取得の要否・ネットワーク前提を
明記する。必要な最低Goバージョンを下げる場合は、互換性を確認した別変更とする。
なお、今回追加で発生した共有Goキャッシュへの書き込み権限エラーは環境固有であり、
この指摘の根拠とは分けている。

## 分野別の評価と残る範囲

| 分野 | 評価 |
|---|---|
| Go契約 | 小さな標準ライブラリ依存のインターフェース。入力所有権・適用不可・失敗時の結果・sentinel errorの区別は明確。検証器や計算器がないのは宣言された設計どおり。 |
| 仕様と探索の分離 | 宣言的な `Complete` / 最短到達距離と、有限目標探索が別定義になっている。単なる探索結果の再定義を正当性証明と呼んでいない。 |
| 面子手の一般探索 | 手牌消費・不足数の不変条件、候補被覆、最小値一致・存在一意性を確認。保証は `ValidCounts` と13枚相当の条件下であり、Go入力全域ではない。 |
| バッチ走査 | 与えられた分解から走査と最終雀頭を構成する出口が存在。分解の重複度を順列で保つ設計は妥当。ただし、この分解自体が全手牌を覆うとは主張できない。 |
| 七対子 | 異なる7対という完成条件、13枚手から7手以内の完成経路、総合値6以下への接続がある。任意手の計算可能な値と仕様の一般的一致までは未実装。 |
| 国士無双 | 有効13枚手の値の存在・最大値13の達成を確認。`kokushiShanten` と仕様の一般的一致とは別成果であり、現行文書も区別している。 |
| 構成・依存 | 公開import入口、形に依存しない交換基盤、`Scan` / `Search` の分離は読みやすい。Lean・Mathlibと推移依存のコミットは固定されている。 |
| 文書 | 現行計画・台帳と過去レビューの区別は概ね明確。過去の指摘を現在の未解決問題としてそのまま再掲すべきではない。 |

### 不具合と混同しない後続課題

- **14枚相当手牌:** Go契約には含まれるが、一般探索の現在の仕様一致・全域性定理は
  13枚相当が対象。関数が呼べることと、14枚での正当性を証明したことは別である。
- **総合計算器:** `OverallShanten` は宣言的・非計算可能な仕様であり、それ自体は問題ない。
  3形の計算可能な実装とGoへの接続は別途必要。Lean仕様の `none` をそのまま
  Goの「適用不可」や成功扱いへ変換してはいけない。
- **性能:** 現行探索は全完成候補の列挙であり、数値の正しさの証明は実用的な時間・
  メモリの保証ではない。通常の固定面子なしの13枚手での性能は今回確認できていない。
  Go移植前に基準値・測定環境・資源上限を定めて評価する必要がある。
- **旧搭子モデル:** `Taatsu.sequence` は連続2枚と一意の補充先を表し、一般の嵌張を
  直接持つ型ではない。嵌張にも対応する新一般探索と、旧分解・走査の被覆範囲を
  [用語集](./GLOSSARY.md) や [ブロック説明](./SHANTEN_BLOCKS.md) でも区別するとよい。
- **小さな文書不整合:** [README](../README.md#errors-and-ownership) の並行利用説明と
  [用語集](./GLOSSARY.md) のバックエンド説明には `v1` が残る。現契約の `v2` との
  関係を整理したいが、現時点でコードの挙動を変える問題ではない。

### 証明の信頼境界

| 定理群 | 確認した依存 |
|---|---|
| 一般探索の仕様一致・存在一意性・最適状態（3件） | `propext`、`Classical.choice`、`Quot.sound` のみ |
| 国士無双の最大値・具体例の仕様値（2件） | 同上 |
| 共有の完成経路構成・不足数下界（2件） | 同上 |
| 分解からバッチ走査（1件） | 上記に加え、牌種順の網羅性の `native_decide` 依存 |
| 七対子の完成上限・総合値6以下（2件） | 上記に加え、未登場牌種の存在の `native_decide` 依存 |

`native_decide` は証明穴とは異なるが、コンパイル・実行結果を信頼する境界を追加する。
この違いは台帳にも記載されており、今回新たに生じたものではない。
厳密なカーネル検査だけの依存へ統一するかは、プロジェクトの保証方針として判断する。

## 推奨する次の順序

1. R1の共有遷移の有効性を整理し、保存定理と反例の回帰検査を追加する。
2. R3の自動検証とR4のGo環境整合を、小さな独立変更で整える。
3. R2の容量付きモデルを設計し、上記A/Bの差を受入例にする。
4. 14枚相当・七対子／国士の一般計算・総合値・Go対応を、対象条件付きで順に接続する。
5. 正しさの基準を維持したまま性能測定・枝刈り・メモ化へ進む。

既存の抽象モデルの成果は再利用可能であり、全面的な書き直しを勧めるものではない。
重要なのは、証明した範囲とGo契約全体との間に必要な対応条件を明示して埋めることである。

## 付録：R1の再現用Leanコード

以下を `lake env lean -j2 --stdin` へ入力して検査できる。

```lean
import Shanten
open Shanten

def reviewEast : Tile := .honor ⟨0, by omega⟩
def reviewNorth : Tile := .honor ⟨3, by omega⟩

def reviewBefore : Hand :=
  { counts := fun tile =>
      if tile = reviewEast ∨ tile = .honor ⟨1, by omega⟩ ∨
        tile = .honor ⟨2, by omega⟩ then 4
      else if tile = reviewNorth then 1 else 0
    fixedMelds := 0 }

example : IsThirteenTileHand reviewBefore := by
  unfold IsThirteenTileHand ValidCounts
  decide

example : HandStep reviewBefore
    (exchangeHand reviewBefore reviewNorth reviewEast) :=
  exchangeHand_step reviewBefore reviewNorth reviewEast
    (by decide) (by decide)

example : ¬ ValidCounts
    (exchangeHand reviewBefore reviewNorth reviewEast) := by
  intro h
  have hcount := h reviewEast
  change exchangeCounts reviewBefore reviewNorth reviewEast reviewEast ≤ 4 at hcount
  rw [exchangeCounts_drawn _ _ _ (by decide)] at hcount
  change 4 + 1 ≤ 4 at hcount
  omega
```

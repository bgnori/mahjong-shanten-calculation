# MentsuHand.lean 追補レビュー：前回から妥当な進捗があるか

## 判定

**妥当な進捗はある。前回と同じ作業を繰り返しているだけではない。ただし、完成したのは主に「選択列の並べ替え」であり、「分解から実際の探索経路を作る」という中心課題は未解決である。**

今回の約45分間について「進捗がない」とするのは厳しすぎる。前回指摘した順序依存に対し、重複度を保つグループ化と、その結果が元の列の順列になることを実際に証明している。一方、直近の接続補題は必要な経路を前提としており、**その経路を分解から作る証明までは進んでいない**。

評価を分けると次のとおり。

| 評価対象 | 判定 |
|---|---|
| 前回レビューへの対応方向 | 妥当。順序・重複度と、探索の対象範囲を修正している |
| 選択列のデータ変換 | 明確な前進。牌種順グループ化の順列性は完成 |
| 分解から妥当な状態遷移を構成すること | 未完成。新しい包含関係を遷移証明にまだ接続していない |
| 雀頭を含むグループの処理 | 未解決 |
| 任意の分解の34牌種順バッチ走査 | 未完成 |
| 一般13枚手・最小値一致への拡張 | 今回の新規成果には含まれない |

したがって、**今回までは必要な準備として説明可能だが、次も「経路があれば別の関係へ変換する」補題だけを追加し続けるなら、再び統合が停滞していると判断すべき**である。所要時間の適否やモデルの内部状態までは、コミット履歴だけでは断定しない。

## 前回指摘の対応状況

### R1：順序を変えるのに部分列を要求していた問題

**判定：データ層は改善、遷移層は未解決。**

次は新規成果として認めてよい。

- [MentsuHandChoiceSubmultiset](../Shanten/MentsuHand.lean#L1699) はリストを `Multiset` として比較し、順序を固定せず重複度を保持する。
- [mentsuHandChoicesGroupedByTiles](../Shanten/MentsuHand.lean#L260) は、牌種ごとに選択を取り出し、残りを後続牌種へ渡す。
- [残余列の空性](../Shanten/MentsuHand.lean#L385) と [グループ列全体の順列性](../Shanten/MentsuHand.lean#L442) により、代表牌が対象牌種列に含まれる選択を漏らしたり増やしたりしないことを示した。

ここは前回にはなかった、まとまった成果である。レビュー側でも、順列性の定理を**任意の `MentsuHandBlockDecomposition` の `blockChoices` と34牌種順に適用できる**ことをLeanで確認した。前提が実際の対象へ適用できないだけの空疎な補題ではない。

ただし、新しい `MentsuHandChoiceSubmultiset` の使用箇所は、その基本性質と単一グループの包含までである。次の既存証明は引き続き `List.Sublist` を要求している。

- [valid_next_choice_of_sublist](../Shanten/MentsuHand.lean#L2324)
- [completion_respects_of_sublist](../Shanten/MentsuHand.lean#L2521)
- [forward_of_sublist](../Shanten/MentsuHand.lean#L3994)
- [batch_of_representative_group](../Shanten/MentsuHand.lean#L4069)

**「新しい関係を定義した」ことと「順序を変えた途中状態から次の遷移を証明できる」ことは、まだ別である。** 前回止まった実際の呼び出し箇所には、新しい関係が届いていない。

### R2：旧一選択走査とバッチ走査の不一致

**判定：方針の修正は妥当。一般走査の構成は未完成。**

旧一選択走査との単純な同値を目標から外し、バッチ走査を正式な中間関係とする方針は前回の反例に整合する。

新しい [AppliesMentsuHandGroupedTileBatches](../Shanten/MentsuHand.lean#L2945) は、牌種ごとのフィルタ列をバッチ処理し、残りの列を再帰的に処理する関係である。[to_scan](../Shanten/MentsuHand.lean#L2962) によって、これを既存の牌種順バッチ走査へ変換できる。

ただし、この関係の存在を、任意の分解から構成する定理はまだない。関係を定義して変換を証明したことは有用だが、その関係を満たす経路を得たことにはならない。

### R3：狭い分解だけで全13枚手をカバーしようとしていた問題

**判定：説明上は修正。一般手牌対応の実装は今回進んでいない。**

計画と進捗台帳では、雀頭・4ブロックが既にある分解と、雀頭なし・孤立牌・ブロック不足を含む一般手牌を区別するようになった。これは必要な修正であり、未完了範囲を隠しているとは評価しない。

一方、分解構造を一般化したわけではなく、全手牌の最小値をカバーする新たな構成や評価関数は追加されていない。これは今回の狭い目標から除外した課題であって、解決済みではない。

### R4：雀頭を含むグループへ既存補題を適用できない問題

**判定：未解決。認識はされているが、証明上の改善はない。**

[forward_of_sublist](../Shanten/MentsuHand.lean#L3994) と [batch_of_representative_group](../Shanten/MentsuHand.lean#L4069) は引き続き、処理する全選択が非雀頭であることを要求する。

[MentsuHandChoiceStateMatches](../Shanten/MentsuHand.lean#L3399) も、使用牌・面子数・搭子数だけを保持し、雀頭を既に処理したかどうかと `state.pair` の対応を含まない。今回、これを補う雀頭用不変条件や、雀頭を含むグループを実際に処理する定理は追加されていない。

新しい経路→バッチ変換それ自体は雀頭を排除しない。しかし、その入力となる経路を分解から供給するところが未解決である。

最後の [step_of_forward](../Shanten/MentsuHand.lean#L3559) の主要前提は次のとおり。

```lean
(hpath :
  AppliesMentsuHandChoicesForwardWithCopyLimit hand
    state (mentsuHandChoicesForTile tile source) middle)
(htail :
  AppliesMentsuHandGroupedTileBatches hand tiles
    (mentsuHandChoicesWithoutTile tile source) middle final)
```

これらを受け取ってコンストラクタを適用している。**`hpath` と `htail` を分解から生成する再帰構成が、依然として呼び出し側の仕事として残る。**

よって、「グループの経路があれば走査へ接続できる」という報告は正しい。「フィルタ列から経路を作れた」「分解から全走査を作れた」と読み替えると過大評価になる。直近の作業報告自体は、中心課題が残っていることも明記している。

## 次回の完了条件

これ以上の補助関係の追加を一律に禁止する必要はない。しかし、次の成果物へ直接つながるものに限定すべきである。

### 最優先：分解から経路を生成する

次の3項目を一つの依存鎖として仕上げる。

1. 処理済み列の重複度付き包含から、次の選択後の使用牌・ブロック数・補完牌の上限を導く。旧 `List.Sublist` を呼び出し側へ要求しない。
2. 雀頭をまだ選んでいない／既に選んだことと `state.pair` を対応付け、雀頭を含むグループも処理する。
3. これらから、実際の分解を入力して `AppliesMentsuHandGroupedTileBatches` または直接 `AppliesMentsuHandTileBatchScan` の存在を返す。

### 統合定理の受入条件

当面の狭い目標は、概ね次の形でよい。

```text
任意の hand と d : MentsuHandBlockDecomposition hand から、
  ∃ final,
    初期状態から、実際の34牌種順で、
    d.blockChoices をグループ化した全選択をバッチ走査でき、
    final.pair = some d.pair であり、
    IsMentsuHandBlockSearchComplete hand final が成立する。
```

**入力として経路・バッチ・探索成功・各遷移の妥当性を要求しないこと**が重要である。そこを仮定すると、今回と同じ未解決部分を別の補題へ移しただけになる。

前回の「東の雀頭と12萬の搭子4組」の有効13枚手で、少なくともこの出口まで通すことも有用な中間マイルストーンになる。今回の変更には、その具体的な全走査の証明は含まれていない。

この狭い統合定理が完成した後に、一般手牌・最小距離の被覆性を別課題として扱う。既存のターゲットDPと仕様の一致は以前から完成しているため、次回も新規成果に数えない。

## 最終評価

**前回からの作業には合理性があり、データ層では検証可能な進捗がある。ただし、前回「ここを直さないと出口へ届かない」とした、途中状態の妥当性と雀頭処理は残っている。**

今回を「全面的な停滞」と判定するのは適切でない。一方、「順序問題は解決したので、あとは接続だけ」とするのも早い。次回は行数や接続補題数ではなく、**分解だけを前提にした全走査の存在定理が完成したか、そこへ必要な未解決前提が実際に減ったか**で判定するのがよい。

## 2. 用語・仕様の対応表

| 概念 | shanten側 | 分類側 | W0で確認した対応と境界 |
|---|---|---|---|
| スート・ランク・牌種 | `Shanten.Suit`、34種の`Shanten.Tile`。数牌rankは`Fin 9`で0が1 | `Suit`、`Rank = Fin 9`、34種の`Tile`。数牌rankは0が1 | 対象集合とrank規約は対応候補。コンストラクタ・名前空間・列挙順が異なるため同じLean型ではない。全単射・列挙順の対応を別途示す |
| Int37・物理ID | `Input37.Counts37 = Fin 37 → Int`、赤5を別要素に持つカウント | GoのInt37 APIは牌ごとの値の列。Tenhou APIは物理ID列。Leanの主要待ち定義は34種`List Tile` | Int37の値の規約は既存契約上対応するが、カウント配列・Int37値の列・物理ID列は別表現。136→37→34、重複、容量、射影で失う情報の対応定理は未実施 |
| カウント・多重度 | `Tile → Nat`、`Multiset Tile`、符号付き入力の`Counts37` | Leanの牌種`List Tile`、GoのInt37列またはTenhou ID列 | 多重度は共通の意味候補だが、順序付き列をカウントへ移す変換と保存則が必要。分類の出力順まで同一視しない |
| 対子・雀頭 | `pairTiles`と通常形完成時のpair | `Toitsu`、通常形の`WinningComponent`内のpair | 同じ牌種を2枚使う部品として対応候補。雀頭という役割と、七対子の対という用途は用語上区別する |
| 順子・刻子 | `Meld.sequence`、`Meld.triplet` | `Shuntsu`、`MentsuCandidate`の順子／刻子 | 牌種多重度として対応候補。ただし型・列挙器・標準順は別。構成牌数の保存と証人の対応を証明する |
| 面子・固定面子・槓 | `Meld`は順子または刻子。`Capacity.FixedMeld`は面子または4枚を占有する槓 | `MentsuCandidate`は通常形分解の順子または刻子候補 | 通常形の完成部品は対応候補だが、固定面子は入力文脈として区別する。槓は4枚占有する固定面子であり、通常形分解候補へ混ぜない |
| 牌種容量 | `ValidCounts`は34種カウントの上限4。`Input37.capacity`は赤5=1、通常5=3、その他=4。`Capacity.ValidHand`は固定牌との合算 | `HasLegalTileCounts`は解析対象の牌種列を牌種ごと最大4枚に制限。`IsWaitFor`は候補牌を加えたとき5枚目でないことを要求 | 「4枚制限」は対象集合が異なる。分類の牌姿単独の制限と、shantenの固定牌込み容量を同じ述語と呼ばない。既存Finderが固定面子内容を入力に取らないことは、制約がないことを意味しない |
| 通常形完成・分解 | `Complete .mentsuHand`は完成述語、valid counts、固定面子数と雀頭・面子の証人を含む。容量モデルは固定牌内容も検査 | `WinningPartitionSpec`は雀頭・面子列と入力牌列の順列一致を表す。合法な手牌サイズ・枚数は別の`IsLegalTenpaiHand`、待ちは`IsWaitFor` | 「雀頭1＋順子／刻子」という分解関係が主要な共有候補。分解仕様そのものと、有効な完成手・合法待ちの前提は分離する |
| テンパイ | 改善距離1のシャンテン0。固定面子数と形の適用可能性を含む | `IsWaitFor`は通常形待ち。Leanは1/4/7/10/13枚相当を扱い、Go公開APIは4/7/10/13枚 | 通常形待ちと総合シャンテン0は同じでない。分類の入力サイズ範囲もLeanとGoで異なる |
| 分解の標準順 | 共通の正規順仕様はない | `WinningComponent.canonicalize`は部品順を標準化し、部品と個数を保存 | 分類固有の出力互換仕様として残す。共有核の抽象分解を自動的に分類側の順に固定しない |

### 用語集の現状

- shantenの[用語集](../GLOSSARY.md)は、麻雀一般語、Go契約、Lean概念、
  shanten固有識別子を一文書にまとめる。
- 分類側の[`domain-vocabulary.md`][class-vocab]は和了構成部品、
  標準順、待ち分解・導出・コード・核、可約性など分類固有語が中心。
  Lean構文・タクティクは別の`lean-vocabulary.md`へ分けている。
- 共通用語集の初期候補は、牌種・数牌・字牌・赤5/Int37・カウント、
  容量、対子・雀頭・順子・刻子・通常形分解である。
  ただし「手牌」「面子」「完成」「テンパイ」「4枚制限」は入力・文脈・前提が異なるため、
  一つの説明に早期統合せず、用法を並記して用語境界を決める。
- 待ち核、待ち分解コード、既約性、分類ID、病的プロファイルは分類側に残す。
  シャンテン値、改善距離、固定容量付き探索、七対子・国士無双はshanten側に残す。

## 3. 基準検査結果

検査は固定ソースを使い、リポジトリの依存版を変更せず実行した。

| 対象 | 検査 | 結果 |
|---|---|---|
| shanten | Lean `v4.35.0`: `lake build` | 成功（928 jobs）。既存警告は出たがエラーなし |
| shanten | Go `v1.26.4`: `GOTOOLCHAIN=auto go test ./...`、`GOTOOLCHAIN=auto go vet ./...` | 成功。Goパッケージは`[no test files]`のため、これは契約コードのビルド／vet確認で数値適合テストではない |
| mahjong-formalization | Lean `v4.28.0`: `lake build Mahjong MahjongTests` | 成功（772 jobs）。ビルド前に対象importのmathlib cache 734ファイルを取得 |
| mahjong-formalization | Go `v1.24.5`: `go test ./mahjong` | 成功（0.214秒） |

ホストにはLeanとGoがなかったため、既存shanten開発コンテナで検査した。
初回はコンテナ内Gitの所有者判定とLean artifact cache不足で止まったが、
コンテナ内の特定workspace/dependencyをsafe.directoryに設定し、
分類側は指定mathlib版のcache取得後に再実行して成功した。
Go契約の検査は`GOTOOLCHAIN=auto`により要求版を選択した。
これらの環境準備はソース・manifest・依存指定を変更していない。

## 4. W0の結論と次工程

1. 共有候補は牌種・表現の対応、部品展開、多重度、通常形分解の意味論と、
   それらを説明する共通用語である。これらの同値・全単射・保存定理はまだ証明していない。
2. 容量、完成、テンパイは似た語でも対象範囲が異なる。定義を一つにまとめる前に、
   牌姿単独／固定文脈込み、通常形／全形、候補牌追加前後を明示する。
3. コード・定理・共通用語集を両側の正本にする方向は整合する。
   shantenと分類の用語集全体を統合するのではなく、共有用語の出典と各側の意味差を示す。
4. W1ではLean/mathlibの共通版を試行し、既存証明と回帰を再確認する。
   W2で独立核の配置・ライセンス・文書の公開形式を決めるまではコード移植に進まない。

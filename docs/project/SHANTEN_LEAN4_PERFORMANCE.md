# Leanシャンテン計算の性能測定記録

この文書は性能測定の準備、測定方式の変更、実測結果とその制約を記録する。
現在の実行方法と対象入力は[測定手順](../../benchmarks/README.md)、
証明の成果と未解決条件は[進捗台帳](SHANTEN_LEAN4_PROGRESS.md) を参照する。

## 利用想定と目標

牌譜解析で3タイプのシャンテン数を計算し、
1半荘あたり約800回（18打 × 4人 × 11局 = 792回）の呼び出しを想定する。
平均1ms以下が最低限の性能目標である。
半荘の解析全体を数秒に抑えるためのオーダーとして設定しており、
この目標だけで他の処理を含む解析全体の時間が保証されるわけではない。
平均の対象単位、入力分布、測定範囲、実行方式・環境などの判定条件は
[現行計画](SHANTEN_LEAN4_PLAN.md#利用想定と性能目標)に従い今後定める。
既存の個別ケース測定や時間切れを除外した平均だけでは、この目標の達成を判定できない。

## 短時間計算の測定方針

1回の計算が短い場合は、起動・入力検査の後に同一ケースを基本100回計算し、
合計時間を回数で割って1回あたりの時間を求める。1000回や1万回を前提とせず、
重いケースでは回数を減らした測定も別途記録する。
時間制限は全反復にかかり、時間切れ時は平均を算出しない。
同一ケースの反復平均を牌譜全体の入力分布による平均と混同しない。
実行方法と計測範囲は[測定手順](../../benchmarks/README.md)を参照する。

## 100回反復による測定（2026-11-25）

測定対象はshanten `683c39fb0107f3084d17f64e2c1b65400deccafc`、
Core `86e594624ee5f6a5c7ba35603db9a3f7462525be`、
Mathlib `56a005855ea17e0b0958f73ec801ae140b0a1679`。
測定開始時の各作業ツリーは変更なし。Lean 4.35.0、Python 3.11.2、Linux x86_64、
Intel Core i5-4690、`LEAN_NUM_THREADS=2`、`nproc` で4 CPU、
cgroupのCPU割当は2 CPU相当、メモリ上限は6 GiB。共有環境で、既存のビルド成果物・
OSキャッシュを使った。ネイティブ実行ではなく `lean --run` の測定である。

起動・入力検査後に測定を開始し、同一ケースを100回計算した。単調時計で測った合計を
100で割って平均を求めた。ループ・入力参照・各回の結果一致検査は含み、起動・入力検査・
結果表示は含まない。起動の制限は60秒、計算の制限は100回**全体**で12秒、
結果通知後の終了制限は5秒、各プロセスの仮想アドレス空間制限は12 GiB。
順次実行し、cgroup匿名メモリが3,750 MiBに達した場合は中断する監視を設けた。
監視での中断はなく、匿名メモリの標本最大は約1,840 MiBだった。
計算の時間切れ監視には通信・スケジューリングの遅延が含まれる。
全47実行の日時・順序・回数・結果・出力・制限・メモリ情報は
[生データ](../../benchmarks/baseline-2026-11-25-repeat100.jsonl)を参照。

100回の試行は42バッチで、28バッチが成功、14バッチが計算時間切れだった。
時間切れ時の完了回数と合計計算時間は不明であり、12秒を100で割って
1回の平均やその下限とはしない。以下の時間はミリ秒。複数バッチを測定したケースは
各バッチの合計と平均の最小〜最大を示す。1バッチのみのケースはばらつきが未評価。

### 所見

この代表入力では、特殊形の100回平均は各ケースで1ms未満だった一方、
完了した固定面子4組の面子手は約9.9〜11.0msだった。固定面子0〜3組の面子手は
100回の制限内に完了しなかった。固定面子3組の2例は1回約5.6秒で完了した。
面子手の改善は重要だが、入力分布に基づく牌譜全体の平均や実利用環境での性能を
この結果だけで判定することはできない。全ケースを通した平均・分位点も算出しない。
正常終了したコマンドの最大RSSは約1,717〜1,718 MiBで、Leanの読み込みを含む。
時間切れ時のRSSや並列プロセス合計のピークは正確には得られない。

[測定手順](../../benchmarks/README.md) と、既存の容量付き計算を呼び出す代表入力を用意した。

## 起動と計算の時間制限の分離（2026-11-25）

旧測定では外側の12秒上限にLeanの起動時間が含まれ、
時間切れから計算時間を評価できなかった。
`ShantenBench.lean` の `controlled` モードと
`measure_calculation.py` は、起動・入力検査後の準備完了通知と開始指示を交換し、
起動用と計算用の時間制限を分ける。
計算が完了した場合の `calculation_ns` はLean内の時計で測り、起動と通知処理を含まない。
計算の時間切れ監視には開始・結果通知の通信やスケジューリングの遅延が含まれるため、
計算時間そのものの厳密な下限としては扱わない。詳しい手順と制約は
[測定手順](../../benchmarks/README.md) を参照する。

動作確認として、計算の上限を1秒に設定した実行で `ready-four-13` は
起動約2.52秒の後、計算約11.7ミリ秒で成功した。
`kan-three-13` は起動約2.54秒の後、計算側の監視が約1.00秒で時間切れとなった。
これは方式の動作確認であり、旧測定の全ケースを新方式で再測定したものではない。

## 性能測定の初回結果（2026-11-25）

**旧方式の参考記録:** 時間切れの判定にLeanの起動時間を含めていたため、
計算時間のベースラインとしては不十分。時間切れのケースについて計算時間の下限は分からず、
起動完了後に制限時間を開始する新方式で再測定する。

測定対象はshanten `cdab34e0ab2ec1acdf12631ca4911c806001943e`、
Core `86e594624ee5f6a5c7ba35603db9a3f7462525be`、
Mathlib `56a005855ea17e0b0958f73ec801ae140b0a1679`。各作業ツリーは変更なし。
Lean 4.35.0、Python 3.11.2、Linux x86_64、Intel Core i5-4690、
`LEAN_NUM_THREADS=2`。CPUは `nproc` で4、cgroupのCPU割当は2 CPU相当、
メモリ上限は6 GiB。共有環境で他のプロセスも稼働していた。
既存のビルド成果物・OSキャッシュを使い、クリーンな測定環境ではない。

[測定手順](../../benchmarks/README.md) に従い `lean --run` を順次実行した。
各コマンドは起動を含め12秒で打ち切り、各プロセスの仮想アドレス空間を

### ビルドと所見

`lake build Shanten` の別測定は、12 GiBの仮想アドレス空間制限・120秒上限で
多数のモジュールを再ビルド中、1モジュールでスレッド作成失敗が発生し、
全体も時間切れとなった。続く16 GiB・180秒上限の再実行は、
先の途中成果を利用して49.573秒で成功した。さらに成果物が最新の状態での
増分ビルドは1.171秒で成功した。いずれもクリーンビルドの所要時間ではない。
ビルドの `wait4` 最大RSSは並列子プロセスの合計ピークを示さない。
事前の制限値確認では、8 GiBの仮想アドレス空間制限、および768 MiB・2 GiBの
データ領域制限の各試行で、Leanのスレッド作成が失敗した。これらを計算時間に含めない。

固定面子3組の例は約5.4〜5.5秒、4組の例は約10〜14ミリ秒であり、
固定面子0〜2組の今回の例はすべてコマンド全体の12秒上限に達した。
面子手候補の列挙が性能改善の優先候補だが、この測定だけでは内訳や支配要因を
確定できない。特殊形の閉形式は今回の例ではそれより短い。
1回だけのケースや時間切れを含むため、分位点・最悪時性能は算出しない。
固定面子0〜2組の完了時間と探索内訳は未測定であり、必要なら資源を確保して再測定する。
ネイティブ実行速度ではなく `lean --run` の結果であり、当時は性能目標が未決定だった。

### 共通用語集の正本と利用側文書

共通用語集も共通コードと同じく、独立核リポジトリを正本として版管理する。
単に既存の二つの用語集をコピーして同じものとみなすのではなく、
定義・対象範囲・前提・対応するLeanの型や仕様を一か所で保守する。
コードの識別子だけでなく、同じ語が異なる前提で使われる場合の差も記録する。

- 共通用語集には、牌種と物理牌、136/37/34表現、列とカウント、
  牌種容量、対子・雀頭・面子・槓、通常形分解など、
  共通核のAPIとその定理が依拠する語を置く。
- shantenの[用語集](../GLOSSARY.md)と分類側の語彙文書は、
  各側の入力・出力・探索・分類固有語を残す。共通語を再掲するときは
  共通用語集への参照を付け、定義本文を二重管理しない。
- 一般語が各側で異なる意味を持つ場合、共通語として統一せず、
  用途別の正式語と差分を両側の文書に明記する。
- 共通用語の意味変更は、対応するコード・定理・変更履歴と同じレビュー単位で行う。
  共通核のリリースでは用語集の版もコードの版と一緒に固定し、
  利用側の文書リンクをそのリリースに対応させる。

### 指定ファイル Special.lean の扱い

[Special.lean](../../Shanten/Special.lean)は七対子・国士の式と
最短完成距離の一致を証明しており、通常形分類との共通コードではない。

- `sevenPairsShanten_isShapeShanten`、`kokushiShanten_isShapeShanten`と
  それぞれの不足枚数の会計補題はshantenに残す。
- `isShapeShanten_of_minimum_deficit`も、13・14枚と距離仕様に依存するため残す。
- [Exchange](../../Shanten/Exchange.lean)は既にshanten内部の形非依存部分を分離している。
  「形非依存」と「分類側とも共有可能」は別であり、そのまま独立核へ移さない。
- 共通型導入に必要なimport・対応補題だけを変更し、
  [ProofChecks](../../Shanten/ProofChecks.lean)の特殊形出口の保証を維持する。

## 3. 最初に固定する仕様

以下は**提案する仕様・接続定理**であり、現時点での証明済み定理名ではない。

### 3.1 通常形の共有境界

`StandardCompletion(n, C)`を、雀頭1個と順子／刻子n個の展開カウントが
`C`に一致することとする。4枚制約は分解可能性とは別の述語で組み合わせる。
分解の証人を保持し、存在命題への射影と、個々の分解の対応の両方を用意する。
同じ完成カウントを持つ異なる分解を一つに潰さない。

- shanten：通常形`Complete`と、妥当なカウント・残余面子数・共有分解仕様との同値。
- 分類側：`WinningPartitionSpec`の各分解と共有分解の対応、
  既存の`mem_winningPartitions_iff_spec`への接続。
- 共通型の列挙順と分類出力の正規順は別に扱う。
  型を移しただけで分類IDやシリアライズ順が不変になるとは仮定しない。

### 3.2 固定文脈と通常形テンパイの接続

`C`を手元カウント、`F`を固定牌の占有カウント、`m`を固定面子数、
`n = 4 - m`とする。有効な固定文脈、合算容量、
`m ≤ 4`、手元枚数`3*n + 1`を前提に、次を証明する。

```text
固定文脈込みの通常形待ち(t)
  ↔ 分類側の牌姿単独の IsWaitFor(L, t)
      ∧ C(t) + F(t) < 4

Capacity.IsShapeShanten fixed hand .mentsuHand 0
  ↔ 固定文脈込みの通常形待ちが存在する
```

`L`と`C`の多重度一致、両側の牌種変換も前提に含める。
最初の同値は待ち集合全体、二番目はその非空性を扱う。
13枚相当なので完成距離0は起きず、距離1の一歩は加牌であることも証明する。
通常形待ちの存在を、七対子・国士を含む総合shanten 0と同一視しない。
14枚相当の完成判定・最適打牌との接続は今回の抽出範囲外とする。

分類Leanの1・4・7・10・13枚と、分類Go APIの4・7・10・13枚を区別する。
固定面子込みの新たな評価は接続層に置き、既存Finderの残余形分類を変更しない。

### W0〜W2：着手時の判断と基準固定

1. 既存型・定義・利用する公開定理と、分類出力に影響する列挙／正規化順を棚卸しする。
2. 基準コミットで既存検査を実行し、既存失敗と移行で生じた失敗を分ける。
3. 版統一はshantenのLean／mathlib `v4.35.0`を初期候補とし、
   分類側`v4.28.0`からの移行を独立した変更にする。難航時は共通の別版を再検討する。
4. W2で独立核のリポジトリ名・公開名前空間・保守方針を決め、
   コードと共通用語集の正本をそこに置く。ライセンスはMITとし、
   移植時は既存コードと依存物の著作権表示・ライセンス条件を維持する。
5. 両側の用語集から共通用語を棚卸しし、同義・表記揺れ・前提差・意味の不一致を分類する。
   共通用語と用途固有語を区別し、未解決の語義差を一方へ黙って統一しない。
6. 版更新だけでは出力を変えない。重い全列挙の基準データと再生成の実行条件も記録する。

#### W2決定（2026-11-18）

- **名前体系:** 表示名を「Mahjong + 対象」、リポジトリslugを`mahjong-<対象>`に揃える。
  待ち分類は「Mahjong Wait Classification」／`mahjong-wait-classification`、
  シャンテン数計算は「Mahjong Shanten Calculation」／`mahjong-shanten-calculation`、
  将来の点数計算は「Mahjong Score Calculation」／`mahjong-score-calculation`、
  共有ドメイン核は「Mahjong Domain Core」／`mahjong-domain-core`とする。
  汎用名`mahjong`は将来の統合ライブラリ用に確保し、共有核には使わない。
- **点数計算の範囲:** 牌姿から判定する点数要素を扱い、符・翻を含める。
  ドラ・裏ドラやロン／ツモ等は外部入力として与え、支払い点数への換算は対象外とする。
- **配置先・リポジトリ名:** 共有核は独立した`bgnori/mahjong-domain-core`として作成し、
  `mahjong-shanten-calculation`と`mahjong-wait-classification`が共通の正本として利用する。
  `mahjong-domain-core`は麻雀ドメインの小さなLean基盤であることを表し、
  両利用側や将来の他の利用者にも用途を限定しすぎない名前とする。
- **公開パス移行:** 利用者の実態は未確認だが、名前変更に伴う破壊的変更を許容し、
  Go moduleとimport例も新しいリポジトリ名に揃える。
  パス案は`github.com/bgnori/mahjong-wait-classification`と
  `github.com/bgnori/mahjong-shanten-calculation`。公開済み計算結果は履歴上の固定成果物として扱い、
  旧module pathの互換層は設けない。GitHub Pagesの公開先と参照リンクは改名時に確認する。
  この決定は命名方針であり、GitHub上の既存リポジトリ名やGo moduleはまだ変更していない。
- **名前空間・Lake入口:** Lean名前空間と公開root moduleを`MahjongDomain`、
  Lake package名を`mahjongDomain`とする。既存の`Shanten`／`Mahjong`名前空間との
  衝突を避ける。ソース・証明の正本はこのリポジトリに一つだけ置く。
- **保守:** `@bgnori`を初期の主保守者とし、変更はレビュー可能なPRで取り込む。
  共通核のAPI・用語・リリースを同じ変更管理の下で扱う。
- **ライセンス:** 新規共通核のライセンスにMITを採用する。
  ユーザー確認により対象コードの権利者は`@bgnori`とし、新規核の表示を
  `Copyright (c) 2026 bgnori`とする。共通核には標準MIT `LICENSE`を置く。
  既存コードを移す際は既存の著作権表示を保持し、`mathlib`等の依存物は各ライセンスを尊重する。
  shanten自体のライセンス変更はW2の対象外とする。
- **固定依存・更新:** 利用側の`lakefile.lean`で共通核のGit依存を完全なコミットSHAに固定し、
  `lake-manifest.json`をコミットする。ブランチや可変タグには固定せず、
  共通核を先に検証・公開した後、両利用側を別々の変更で更新する。
- **文書:** 共通用語集の正本を共通核の`docs/GLOSSARY.md`に置く。
  Markdownの英日対訳を基本とし、正式語・定義・適用範囲・前提・対応するLean識別子／定理を記す。
  共通核のREADMEから同文書へ案内し、各利用側の用語集は固有語と意味差を保つ。
  利用側からは採用した共通核の固定コミットまたはリリースを指すリンクを張り、
  共通定義の複製を正本として維持しない。各側で用法が異なる語はローカル文書に差分を明記する。
- **状況確認（2026-11-18）:** `bgnori/mahjong-domain-core`は作成済みで、公開リポジトリとしてアクセスできる。
  `main`ブランチと標準MIT `LICENSE`（`Copyright (c) 2026 bgnori`）を確認した。
  `gh`はGitHubアカウント`bgnori`で認証済みで、GitHub API上の対象リポジトリ権限はpush/admin。
  したがって、リポジトリ名の利用可能性確認とGitHub認証はブロッカーではない。

### W3〜W5：互換層からの段階移行

1. 共通核はmathlibの必要最小限にのみ依存し、利用側への逆依存を作らない。
   広域の`import Mathlib`は使わず、各モジュールは必要な個別モジュールだけをimportする。
   実際に共通するimport集合が現れたら、内部の`MahjongDomain.Prelude`へ集約する。
   公開rootは共有ドメインAPIの入口とし、利用側はそのAPIを使うためだけにmathlibを直接importしない。
2. 最初は既存型と共有型の変換・全単射・保存定理を用意する。
   同じ構造に見える別の帰納型が`abbrev`だけで一致するとは扱わない。
3. 牌表現、容量、部品、分解仕様の順に接続する。
   大きな`Core.lean`や分類の`Basic.lean`をファイルごと移植しない。
4. 各共有概念の定義・前提・Lean識別子・定理への参照を共通用語集に記す。
   共通用語集はコードから独立した補助説明ではなく、共有仕様の文書上の入口とする。
5. 既存の公開import・定義・定理名を互換入口として維持する。
   共通型への直接置換は、アダプタで意味を固定した後、証明負荷を見て小分けに行う。
6. shantenの最小距離探索と分類の全分解列挙は別実装のままにする。
   共通核の初版に探索器・Go実装・ルール可変フレームワークを追加しない。

### W6〜W7：接続保証と定着

1. 接続定理の検査場所を一つ決め、両利用側の固定版を参照する。
   共通核自身に両利用側を依存させず、循環を防ぐ。
2. 共通核の版を先に公開し、両利用側はコミットまたは版で固定して更新する。
   各段階で旧依存へ戻せるようにし、証明移行と意味変更を同時に行わない。
3. 共有仕様・定理・共通用語集の正本は共通核、利用側の入力全体・出力契約と固有用語は各利用側に置く。
   共通核の用語集へのリンクと利用側の差分説明を、[用語集](../GLOSSARY.md)、
   分類側の語彙文書、[Lean構成図](../SHANTEN_LEAN_STRUCTURE.md)に反映する。
4. 更新CIでは共通核と固定した両利用側を検査する。
   巨大な分類レポート再生成は通常CIへ無条件に追加せず、リリース検査として分離する。
5. 共通用語の意味変更・削除・改名はAPI／定理の変更と同じく影響評価し、
   互換語・移行先・利用側文書を更新する。用語集のリンク切れと、
   利用側に残った共通定義の不一致をリリース前に確認する。

## 5. 検証と受入ケース

| 領域 | 検証内容 |
|---|---|
| 表現 | 全136 IDで136→37→34が`id / 4`に一致。全37値の意味・容量、全34値の対応を確認 |
| 集約 | 列の並べ替え不変、総数・加算・多重度の保存。情報を失う射影を逆変換と呼ばない |
| 不正入力 | 負数、赤2枚、通常5が4枚、物理ID重複、固定牌との合算超過を各APIの契約どおり拒否 |
| 分解 | 同じ牌姿の複数分解、同一部品の反復、順列で分解情報・分類出力が失われない |
| 用語 | 共通語の正式表記・定義・前提が共通用語集に一つだけあり、利用側の用語集はリンクと固有の意味差を示す |
| 固定容量 | [既存A/B例](../../Shanten/Capacity/Examples.lean)の値1／0と探索結果を維持 |
| 公開Go範囲のA/B | 手元`111m`＋東、固定3組を「東刻子・123p・123s」と「南刻子・123p・123s」に分ける。牌姿単独の東待ちは共通、固定込みでは前者不可・後者可 |
| 槓 | 同種4枚の固定占有、1固定面子としての枚数換算、暗槓でも特殊形が適用外であることを維持 |
| 特殊形との区別 | `1122334455667z`と么九13種各1枚は総合値0でも通常形分類との比較対象にしない |
| 公開互換 | 分類ID、待ち牌ごとのコード重複度、病的プロファイル、エラー分類、shantenのGo契約を維持 |

### 実行する検査

- 小さな移行ごと：変更したLeanモジュールと直接依存する出口をビルドする。
- shantenの統合時：`lake build`で既存の`assert_no_sorry`を含めて検査する。
  新しい保存定理・接続定理も同種の推移的`sorryAx`不在検査へ追加する。
- 分類の統合時：`lake build Mahjong MahjongTests`と`go test ./mahjong`。
  重い`MahjongComputations`や全レポート再生成は別途対象・資源・結果を記録する。
- 共通核：公開入口と主要定理の証明穴検査、有限対応検査を実行する。
  `native_decide`等への依存は既存保証と分けて明示する。
- shantenのGo依存・契約に触れる場合：`go test ./...`と`go vet ./...`。
  現状は数値計算器がないため、これらを数値一致テストとは数えない。

共通化後に同じ定義を二度呼んで一致するだけの検査にはしない。
抽出前の固定期待値・既存分類成果物・独立した契約表を残す。
テストは入力全域の同値証明の代わりにせず、証明はGo移植自体の正しさまで主張しない。

## 6. 変更単位・完了判定・未決事項

コミット／PRは原則として次の単位に分け、各単位を検証可能に保つ。

1. 仕様対応表・用語対応表・基準回帰の固定。
2. 分類側のLean／mathlib版合わせ。
3. 独立核の牌・表現・容量、共通用語集と保存定理。
4. 独立核の部品・通常形分解と対応定理。
5. shanten接続、分類接続をそれぞれ独立した変更として導入。
6. 固定文脈付き待ちの接続証明・A/B回帰。
7. 固定依存、互換入口、CI、共通用語集と利用側の語彙・移行文書の整備。

**完了:** 両側が独立核を実際にimportし、表現・容量・通常分解の共有仕様を
出口証明で利用している。共有語彙の正本が共通核にあり、両側の用語集が
それを参照しつつ固有概念と意味差を保っている。既存の数値・分類出力・入力契約・
証明保証が維持され、3.2の接続と再現可能な検査が揃っていること。
型をコピーしただけ、共有ライブラリを作っただけ、テストが一致しただけでは完了しない。

**実装前に決定する事項:** 独立核の名称・配置先・公開名前空間、
ライセンスと著作権表示、共通Lean版、接続証明の検査場所、
共通用語集の公開形式と利用側文書の同期方法、全列挙回帰の実行資源・許容時間。
これはW2で決定する保留項目であり、独立核リポジトリ作成やライセンス変更の承認があったとは扱わない。
所要工数はW0の基準検査とW1の移行試行後に見積もる。

## 結論

**進捗はある。ただし、補助定理の整備が進んだことと、最終目標が解決に近づいたことを同一視できない状態である。**

- 追加された補題は実体があり、添付版・現行版ともLeanで検査に成功した。単にコメントや未証明の宣言を増やしているわけではない。
- 一方、2026-11-15の約7時間で対象ファイルを変更するコミットが87件積まれたが、当初の「任意の有効な分解を牌種順探索へ埋め込む」定理は未完成のままである。
- 停滞感の主因は、**並べ替えに対応しない部分列前提、旧探索とバッチ探索の不一致、ブロック分解が対象とする手牌の狭さ**である。単なるLean構文の難しさだけではない。
- 全完成ターゲットを列挙するDPとシャンテン仕様との一致は、今回の長い補題追加より前に既に証明されていた。これを新規成果として数えてはいけない。

したがって評価は、**「何もしていない」ではなく、「正しい局所補題を増やしているが、出口の命題と中間不変条件の設計が揃わず、統合作業が停滞している」**となる。モデルそのものの能力・内部状態は、このレビューからは判定しない。

## 重要な指摘

### R1 / High：牌種順に並べ替えるのに、累積選択列へ元の順序を要求している

対象：

- [部分列からの次選択の妥当性](../Shanten/MentsuHand.lean#L2006)
- [バッチ追加後のコピー制限](../Shanten/MentsuHand.lean#L3401)
- [牌種バッチ走査後のコピー制限](../Shanten/MentsuHand.lean#L3446)
- 現行版で追加された [forward_of_sublist](../Shanten/MentsuHand.lean#L3586)、[batch_of_representative_group](../Shanten/MentsuHand.lean#L3661)

これらの主要な前提は、概ね次の形である。

```lean
List.Sublist (pre ++ choices) decomposition.blockChoices
```

しかし [blockChoices](../Shanten/MentsuHand.lean#L1608) は「雀頭、面子リスト、搭子リスト」の順であり、牌種順ではない。個々の牌種グループが元の列の部分列であることと、**牌種順に連結したグループ全体が元の列の部分列であることは別**である。

例えば、東を雀頭、萬子12を搭子とすると、元の列は次の順になる。

```text
元の列：     [雀頭 東, 搭子12萬, 搭子12萬, 搭子12萬, 搭子12萬]
牌種順の列：[搭子12萬, 搭子12萬, 搭子12萬, 搭子12萬, 雀頭 東]
```

後者は前者の順列だが部分列ではない。この例は後述R2の有効な13枚手・4枚制限付き分解で実現する。単に不正な選択列を持ち出した例ではない。**この部分列性の否定をLeanで確認した。**

現行版の新しい補題をそのまま牌種ごとに繰り返しても、この前提は一般には供給できない。[completion_respects_of_perm](../Shanten/MentsuHand.lean#L2238) は既にあるが、完成した列全体の順列不変性だけでは、走査途中の各接頭辞に必要な妥当性を供給しない。

**推奨する修正方向**

処理済み列を元の列の「順序を保つ部分列」とするのではなく、「重複度を保つ部分多重集合」、例えば `List.Subperm` 相当で追跡する。使用牌、面子数、搭子数、搭子補完牌の単調性をこの関係へ移す。単なる集合包含では、同一ブロックの複数回使用を制限できないため不十分である。

### R2 / High：バッチ走査から旧一選択走査への単純な同値化は成立しない

対象：

- [reachableOnTilesFromWithCopyLimit](../Shanten/MentsuHand.lean#L2475)
- [AppliesMentsuHandChoiceBatch](../Shanten/MentsuHand.lean#L2524)
- [AppliesMentsuHandTileBatchScan](../Shanten/MentsuHand.lean#L2567)
- [バッチ走査から到達性への変換](../Shanten/MentsuHand.lean#L3496)

旧関係は牌種リストの1要素につき1回しか選択できない。バッチ関係は同じ牌種で複数回選択できる。これは単なる表現の違いではない。

**具体例**

```text
手牌：11112222萬 東東 9筒 9索 北   （13枚、各牌種4枚以下）
分解：雀頭 東東、搭子12萬を4組
完成：111122223333萬 東東        （14枚、各牌種4枚以下）
```

この分解は、現在の `MentsuHandBlockDecomposition` の全条件を満たす。一方、搭子12萬を選べる牌種位置は1萬・2萬の2か所しかない。旧一選択走査では同じ搭子を4回選べない。

確認に際しては、候補を代表牌だけに制限していない点にも注意した。[choicesForTile](../Shanten/MentsuHand.lean#L327) はブロックに含まれるどの牌種でも選べる。それでも、この例では2位置に4選択が必要なので不可能である。

Leanで、一選択走査に対して

```text
特定選択の出現回数 ≤ その選択に含まれる牌種の走査位置数
```

を帰納法で証明し、この有効分解の選択列を旧走査で生成できないことまで検査した。

現在のバッチ走査からの変換先は、牌種順を捨てた `reachableWithinWithCopyLimit` である。これは有用な健全性の部品だが、旧牌種順探索への接続が済んだことは意味しない。

**推奨する修正方向**

「旧探索との同値を後で確認する」のではなく、バッチ探索を正式な探索定義にするか、旧探索を置き換えるかを先に決める。全分解を保持したままの単純な同値化は、この例で否定される。

なお、これは「この手牌について旧探索が一切成功しない」という主張ではない。別の分解を探索できる可能性と、**任意の指定分解をそのまま列挙できる**という要求は区別する必要がある。

### R3 / High：任意のブロック分解の列挙ができても、全13枚手・全ターゲットの完全性には届かない

対象：[MentsuHandBlockDecomposition](../Shanten/MentsuHand.lean#L1427)

この構造は、入力手牌に既に次のものがあることを要求する。

- 実在する雀頭2枚。
- 面子・搭子・固定面子で合計4ブロック。
- 各搭子を所定の方法で補完した完成形が4枚制限を満たすこと。

したがって、孤立牌や不足する雀頭・ブロックを許す一般の部分分解ではない。搭子も対子・連続2牌だけで、嵌張や孤立牌を直接表すものではない。

例えば「19萬19筒19索 東南西北白發中」を各1枚ずつ持つ有効な13枚手では、雀頭がないので、この分解構造の値は存在しない。

この点は次の一般命題としてLeanで確認した。

```text
(∀ tile, hand.counts tile ≤ 1)
  → ¬ Nonempty (MentsuHandBlockDecomposition hand)
```

理由は `targetWithinHand` が雀頭の牌種について少なくとも2枚を要求するからである。一方、この手牌についても、既存のターゲットDPは面子手シャンテンの存在を保証する。

よって、「任意の有効分解を列挙する」を完成させても、それだけから次は導けない。

- 任意の有効な13枚手でこのブロック探索が完成すること。
- 全完成ターゲット、あるいは最小距離を達成するターゲットをこの分解で表現できること。
- この探索の最小評価値がターゲットDPの最小値と一致すること。

これは既存の条件付き定理が誤っているという指摘ではない。**進捗台帳にある「完全性を示せば逆方向の包含・一般到達上限へ進める」という見通しには、さらに表現力・被覆性の証明が必要**という指摘である。

**推奨する修正方向**

目的を二つに分ける。

1. 現在の狭い分解構造に対する列挙定理。
2. 一般手牌の最小距離を保つ探索アルゴリズムの正当性。

後者を目標とするなら、孤立牌・雀頭なし・ブロック不足を扱う評価と探索、または完成ターゲット側からの構成が必要である。前者だけを当面の成果物にするなら、それで全手牌の完全性が完了するとは報告しない。

### R4 / Medium：直近の「グループから経路・バッチ」の補題は雀頭を処理できない

対象：現行版で追加された [forward_of_sublist](../Shanten/MentsuHand.lean#L3586)、[batch_of_representative_group](../Shanten/MentsuHand.lean#L3661)

両方とも次を要求する。

```lean
∀ choice, choice ∈ choices → choiceUsesPair choice = false
```

これは「先頭以外が雀頭でない」ではなく、**グループ内の全選択が雀頭でない**という条件である。`hpairEmpty` があっても、この前提自体は消えない。したがって雀頭を含む代表牌グループには適用できない。

直前の作業報告では「先頭以外が非雀頭」という説明になっていたが、実際の型はそれより強い。雀頭用の基底ケースを別途作るか、処理済み列に雀頭が含まれるかを追跡して、各段階で `state.pair` と対応付ける必要がある。牌種順を守る場合、雀頭を無条件に最初へ処理すれば済むわけでもない。

この制約は添付版より後の106行の追加に対する指摘であり、添付版にこの2補題が存在していたという意味ではない。

## 既に完成しているもの／まだ完成していないもの

### 完成済みと認めてよい

- 有効カウントと `tileCount hand + 3 * hand.fixedMelds = 13` を前提にした、[ターゲットDPと形シャンテン数の同値](../Shanten/MentsuHand.lean#L6415)。
- [有効13枚手に対する面子手シャンテンの存在](../Shanten/MentsuHand.lean#L6457)。
- 適切なブロック分解・完成探索状態が与えられた場合の、完成ターゲットの構成や条件付き到達性。
- バッチ・前向き経路の連結、状態・履歴の保存など、追加された個々の補題。

### 完成したと評価してはいけない

- 任意の分解から、固定された34牌種順のバッチ走査を構成する一般定理。
- 旧牌種順探索とバッチ探索の一般的な同値。
- 全有効手牌の最小値をカバーするブロック探索。
- ブロック探索の実行可能な最小値関数と `IsShapeShanten` の値一致。

特に末尾の [exists_isShapeShanten_mentsuHand_of_constrainedBlockSearchOnTileOrder](../Shanten/MentsuHand.lean#L6787) は、探索成功を**仮定して何らかの仕様値の存在**を示す定理である。探索の全域性や、探索が計算した値との一致を述べているわけではない。

また、冒頭の証明地図と第10章の「完結させます」という説明は、この区別が見えにくい。最終目標を示す説明として読むべきであり、現在すべて完了していることの証拠にはならない。

一時Leanファイルでは、R1の並べ替え列が部分列でないこと、R2の手牌・分解の妥当性と旧走査での生成不可能性、R3の有効な全単牌13枚手に分解が存在しないこと、R4の雀頭除外条件を検査した。最初の検査コードの型推論エラーを修正した後、全検査に成功している。一時検査ファイルはレビュー対象の実装に追加していない。

Lean検査の成功は、宣言された命題の証明が通ることを意味する。必要な命題がすべて書かれたことや、前提が実際の統合先で満たせることまでは保証しない。今回の主要指摘はまさにその部分である。

なお、元の仕様モデルで固定面子の牌内容を持たない制約は既知の別課題であり、今回の停滞原因の新規指摘には数えていない。

## 次に依頼すべき作業

「続けて補題を追加」ではなく、次の順で成果物を指定するのがよい。

1. **最終定理の型を先に固定する。** 当面の目標を「与えられた分解のバッチ列挙」とするのか、「全13枚手で値が一致する計算器」とするのかを分離する。
2. **正式な探索を決める。** 旧一選択走査を最終対象に残すなら、任意分解の保持ではなく、代替分解や最小値の保存という別の主張が必要。バッチへ置き換えるなら、末尾の探索インターフェースまで対象を揃える。
3. **順序によらない途中状態の不変条件を1組作る。** 重複度付き部分集合と雀頭使用状況を追跡し、R1・R4を同時に解消する。
4. **具体例を出口まで通す。** R2の13枚手から34牌種順バッチ走査を構成し、最終状態の完了条件まで示す。その後に任意の分解へ一般化する。
5. **その先で一般手牌への被覆性と最小値保存を扱う。** R3の全単牌手も対象に入ることを確認する。狭い分解の列挙だけで全手牌対応完了とはしない。

次回の進捗判定は、「補題を何個追加したか」ではなく、**固定した最終定理で呼び出し側が供給しなければならない未解決前提が減ったか／定理自体が完成したか**で行うのが適切である。現状から責任ある完成率や残り所要時間を数値で示すことはできない。
